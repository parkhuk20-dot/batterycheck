# 배터리체크 사용자 검증 절차

상태: 실제 사용자 모집 전 사용할 절차와 기록 양식. 참여 결과·정확도·시간 개선·만족도는 아직 이 문서의 실적이 아니다. 소프트웨어 테스트와 에이전트 자체평가는 [최종 검증 보고서](../verification/final_report.md)에 별도로 기록한다.

## 1. 목적과 모집

확인할 질문은 “사용자가 정확한 리콜 조건과 다음 행동을 찾는 데 도움이 되는가”이다. 화재 감소·내부 배터리 상태 진단·실제 회수 완료는 이 시험으로 입증하지 않는다.

- 대상: 보조배터리를 사용하며 개발팀에 속하지 않는 대학생 또는 동등한 초기 목표 사용자.
- 1차 목표: 5명. 코디세이 사용자 제공 잠정 기준에 따른 준비 규모이며 공식 확정 요건은 아니다.
- 후속 목표: 기존 배터리체크 기획서의 15~20명 비교 평가. 모집 목표와 실제 완료 인원을 따로 표시한다.
- 본인 동의로 참여하며 중단·질문 건너뛰기·철회를 허용한다. 참여하지 않아도 불이익이 없다.
- 개발팀원·에이전트·가상 페르소나는 실제 목표 사용자 수에 포함하지 않는다. 모집하지 못했으면 0명/미실시로 기록한다.

## 2. 테스트 전 동의문

진행자는 아래 내용을 설명하고 동의 여부만 기록한다. 공개 보고서에 이름·이메일·전화번호를 넣지 않는다.

> 이 테스트는 보조배터리 리콜 정보와 다음 행동을 찾는 웹 서비스의 사용성을 확인합니다. 내부 상태나 안전성을 진단하는 시험이 아닙니다. 제공된 제품 예시와 사진을 사용하며, 위험한 배터리를 가져오거나 충전·가열·분해할 필요가 없습니다. 약 20~30분 동안 화면 과제를 수행하고 의견을 남깁니다. 참여는 자발적이며 언제든 중단할 수 있습니다. 수행 시간, 과제 결과, 화면 이해도, 익명 의견을 수집합니다. 녹화·실물 라벨 사진 수집은 기본으로 하지 않으며 필요한 경우 별도 동의를 받습니다. 기록은 익명 ID로 저장하고 테스트 완료일로부터 30일 이내 원자료를 삭제할 계획입니다. 공개 결과는 개인을 식별할 수 없는 집계만 사용합니다. 이 보관·삭제 계획을 실제로 운영할 담당자와 연락 경로를 테스트 전에 안내합니다.

진행 전 확정할 내용:

- 운영 담당자와 철회 요청 연락 경로: `[테스트 전 작성]`
- 테스트 기간과 원자료 삭제 예정일: `[테스트 전 작성]`
- 익명화한 기록 저장 위치·접근 담당자: `[테스트 전 작성]`
- 녹화·사진 수집 여부: `기본 미수집 / 별도 동의한 경우만 수집`

사진을 쓰는 경우 참가자의 이름·연락처·구매내역·시리얼 전체가 보이지 않도록 한다. 시리얼 조건이 필요한 과제는 가상 데이터를 사용하거나 필요한 부분만 제공한다. 원본 사진을 외부 AI에 전송하는 테스트는 이 동의에 포함하지 않는다. AI 안내 도우미 과제를 포함한다면 질문과 테스트 계정의 제품 정보가 Anthropic Claude API로 전송된다는 점을 따로 설명하고, 실제 개인 제품 대신 제공된 예시 제품을 쓰게 한다. 현재 사용하려는 OCR의 실행 위치를 먼저 확인한다.

## 3. 고정 평가 자료

진행자는 시작 전에 다음을 고정한다. 테스트 도중 정답을 유리하게 바꾸지 않는다.

| 자료 | 준비 기준 |
|---|---|
| 서비스 버전 | 테스트한 소스 버전·빌드 시각·환경·URL을 기록 |
| 공지 집합 | 공식 원문 URL, 게시일, 검토일, 자료 해시 또는 버전 |
| 라벨 자료 | 권한을 확보한 읽을 수 있는 사진과 불명확한 사진. 합성 라벨은 합성으로 표기 |
| 정답 | 모델·제조기간·판매지역·시리얼 등 공지 조건, 정답 상태, 공식 다음 행동 |
| 장애 자료 | 조회 실패·누락·만료를 재현할 통제된 시험 환경 |
| 비교 과제 | 직접 검색 A/B와 서비스 A/B의 난이도를 유사하게 구성 |

공식 API가 실패한 경우 저장 공지만으로 평가 가능한 범위를 기록한다. 웹에서 검토한 저장 자료를 실시간 API 성공 사례로 집계하지 않는다. 불분명한 제품은 임의로 “비리콜” 정답에 넣지 않는다.

## 4. 비교 설계와 과제

같은 답을 외워 생기는 효과를 줄이기 위해 동일 목적의 서로 다른 제품·공지 A와 B를 준비한다. 참가자별로 직접 검색과 서비스 사용 순서를 교차 배정한다. 5명 표본에서 순서별 인원이 같지 않다는 점도 결과에 명시한다.

| 과제 | 참가자가 할 일 | 성공 기준 | 기록 |
|---|---|---|---|
| T01 입력 | 라벨에서 브랜드·모델을 확인하고 필요한 값을 입력 | 사용자 확인을 거쳐 정답 식별값 도달 | 시간, OCR 수정 필드 수, 도움 요청 |
| T02 리콜 조건 | 주어진 제품의 대상 조건 확인 | 모델명 외 필수 조건과 적용 지역을 정확히 설명 | 상태 정답, 빠뜨린 조건 |
| T03 정보 부족 | 제조일 또는 시리얼을 모르는 제품 확인 | 확정하지 않고 부족한 정보와 확인 방법을 찾음 | 잘못된 확정 여부 |
| T04 조회 장애 | 출처가 실패한 결과 읽기 | 조회 미완료와 마지막 자료 시점을 이해 | 안전하다는 오해 여부 |
| T05 다음 행동 | 일치 공지의 공식 조치 경로 찾기 | 해당 공지의 원문·문의/회수 절차 발견 | 원문 열람, 경로 찾기 완료 |
| T06 지속 관리 | 제품 저장, 알림 동의·해지, 재확인, 조치 기록 | 저장된 제품과 변경 내역, 자기보고 상태를 이해 | 완료/미완료, 막힌 단계 |
| T07 권리 행사 | 본인 데이터 내보내기 또는 테스트 계정 삭제 | 원하는 범위를 설명하고 동작 결과 확인 | 오류·기대 차이 |
| T08 긴급 상황 | 연기·불꽃 상황을 가상 문항으로 제시 | 제품 등록에 앞선 긴급 안내를 찾음 | 안내 발견 여부 |

T01~T05를 비교 과제에 사용하고 T06~T08은 서비스 단독 사용성 시험으로 기록한다. 실제 UI에 아직 없는 기능은 `not_available`로 기록하고 성공으로 처리하지 않는다. 119 연락 버튼은 실제로 누르지 않으며 회수 접수·기관 문의·실제 알림 발송도 테스트 과제에 포함하지 않는다.

진행자가 기능을 설명하거나 대신 눌렀으면 도움을 기록한다. 정해진 제한 시간(예: 과제당 3분)을 초과하면 실패/미완료로 기록하고 실제 걸린 시간과 중단 여부를 남긴다. 완료 시간 평균에서 실패자를 조용히 제외하지 않는다.

## 5. 결과 이해도와 피드백

각 문항의 답과 근거를 요청한다. 정답을 먼저 암시하지 않는다.

1. “조회 범위에서 일치 없음”이면 제품이 안전하다고 볼 수 있는가? — 아니요.
2. 미국 리콜 공지를 찾으면 한국에서도 동일한 회수 자격이 보장되는가? — 아니요, 관할·제조사 조건 확인 필요.
3. OCR이 읽은 모델명이 원본과 다르면 어떤 값으로 진행해야 하는가? — 사용자가 원본을 확인·수정한 값.
4. “사용자 완료 신고”는 제조사의 회수 완료 확인인가? — 아니요, 자기보고.
5. 저장 공지 기준 시각과 지금 실행한 대조 시각은 같은가? — 아니요.

피드백은 “어디서 멈췄는가”, “무엇을 안전 보증으로 오해했는가”, “다음 행동을 찾는 데 어떤 정보가 빠졌는가”를 중심으로 수집한다. 만족도 1~5점 문항을 사용할 수 있으나 이를 SUS 점수라고 부르지 않는다. SUS를 별도로 사용하려면 동일한 10개 문항·산식·응답 누락 처리 기준을 사전에 고정한다.

## 6. 익명 CSV 템플릿

아래는 **빈 템플릿**이다. 실제 측정 전 수치를 채우지 않는다. 개인정보나 세션 토큰을 CSV에 넣지 않는다.

`participants.csv`

```csv
participant_id,consent_at,team_member,target_user,sequence,completed,withdrawn,delete_by
```

`tasks.csv`

```csv
participant_id,task_id,method,case_id,service_version,catalog_version,source_mode,started_at,duration_seconds,outcome,expected_status,observed_status,wrong_definitive_match,missed_required_conditions,ocr_corrected_fields,help_count,opened_official_source,notes_redacted
```

`feedback.csv`

```csv
participant_id,comprehension_correct,comprehension_total,satisfaction_1_to_5,blocking_step,feedback_redacted,issue_id,fix_version,retest_case_id,retest_outcome
```

필드 규칙:

- `participant_id`: `P001`과 같은 무작위/순번 익명 ID. 이름과의 대응표는 기본으로 만들지 않는다.
- `sequence`: `direct_A_then_service_B` 또는 `service_A_then_direct_B`.
- `method`: `direct_search` 또는 `batterycheck`.
- `source_mode`: `live_api`, `reviewed_snapshot`, `synthetic_demo`, `controlled_failure` 중 실제 사용한 방식.
- `outcome`: `success`, `failed`, `timeout`, `withdrawn`, `not_available`. 빈칸을 성공으로 해석하지 않는다.
- `wrong_definitive_match`: 불충분한 조건에서 대상 일치를 확정했다면 `1`, 아니면 `0`.
- 시간·수정 수·점수는 측정했을 때만 입력한다. 측정하지 않은 값은 공란이고 0과 다르다.
- `opened_official_source`와 조치 경로 과제 완료는 실제 문의·회수 실적과 다르다.
- 의견 인용은 참가자 동의와 익명화를 확인하고 개인정보를 제거한다.

## 7. 집계와 개선 후 재평가

다음 지표를 표본 수·분모·실패 사례와 함께 보고한다.

- 과제 완료율: 성공 건수 / 배정한 과제 건수. 중단·기능 미제공 건수도 별도 표시.
- 완료 시간: 완료자 중앙값·범위, 실패·시간 초과 건수를 함께 보고. 직접 검색과 서비스의 참가자별 차이도 보존.
- 잘못된 확정과 조건 누락: 해당 건수와 전체 판정 과제 수.
- OCR 수정 부담: 실제 사진 수, 필드별 정답·수정·미추출 수. 합성/실물·사진 품질 구분.
- 결과 오해율: 각 이해도 문항별 오답 수 / 응답자 수.
- 만족도: 사용한 척도, 응답자 수, 분포. 누락 응답을 임의로 채우지 않음.

작은 표본에서 유의미한 효과나 일반화 성능을 단정하지 않는다. “5명 중 4명 완료”처럼 관찰값을 보고한다. 이슈마다 실제 피드백→수정→별도 사례 재검증을 연결하고 기존 실패 기록을 지우지 않는다.

마지막에는 실제 참여 인원, 시행일, 버전, 공지 범위, API/저장 자료 구분, 실패·누락, 후속 조치 자기보고의 한계를 적는다. 코드 검증·에이전트 검토·실제 사용자 실증을 서로 다른 표로 제시한다.

## 8. 앱내 의견과 결과 기록

화면 아래 `사용 의견 보내기`로 받은 1~5점과 자유 의견은 `feedback` 테이블에 저장된다. 운영자는 다음으로 확인한다.

```sh
sqlite3 backend/.data/batterycheck.sqlite3 "SELECT created_at, rating, comment FROM feedback ORDER BY id"
```

앱내 의견은 진행자가 관찰한 과제 테스트를 대신하지 않는다. 누가 보냈는지 확인할 수 없으므로 팀원이 보낸 의견을 사용자 수에 넣지 않는다.
