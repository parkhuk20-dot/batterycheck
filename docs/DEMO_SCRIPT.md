# 배터리체크 10분 발표·시연 구성

상태: 실행 증거를 채워 사용할 발표 초안. 실제 동작과 제한은 [최종 검증 보고서](../verification/final_report.md)를 확인하고 발표 전에 문구를 맞춘다. 공식 본선은 발표 10분과 질의응답 10분이며 서비스 시연을 포함한다. [공식 주요 안내](https://www.devcontest-digitalsolveup.kr/summary?c=1)

## 1. 발표 전 준비

- 테스트 계정·제품·가상 라벨을 사용한다. 화면에 비밀번호·토큰·연락처·실제 시리얼 전체를 노출하지 않는다.
- 빌드·서버·브라우저 확인, 지원 출처·공지 버전·검토일 확인, 시연 계정의 알림 동의 상태를 확인한다.
- 실제 공식 공지, 검토한 저장 자료, 가상 시험 공지를 화면과 말로 구분한다.
- OCR은 실제 실행 엔진을 확인하고 말한다. Mac의 Apple Vision, 컨테이너의 Tesseract, 직접 입력 중 실행한 경로만 주장한다.
- CPSC API가 실패하면 해당 상태를 보여준다. 저장 자료를 최신 API 성공 화면처럼 사용하지 않는다.
- 공개 URL이 없으면 “로컬 실행 시연”으로 소개한다. 컨테이너 파일이 있다는 이유로 배포 완료라고 말하지 않는다.
- 미완성 기능은 계획 슬라이드로만 설명한다. 예비 녹화는 사전 촬영임을 표시한다.
- 119 전화 연결·제조사 문의·실제 회수 신청은 시연 중 실행하지 않는다.

## 2. 10분 흐름

| 시간 | 장면 | 핵심 설명 | 보여줄 근거 |
|---|---|---|---|
| 0:00~1:15 | 문제·사용자 | 보유제품에 맞는 리콜 조건과 다음 행동을 찾고 지속 관리하는 문제 | 인터뷰가 있으면 실제 결과, 없으면 검증할 가설로 표시 |
| 1:15~2:30 | 사진 또는 직접 입력 | OCR은 입력 후보를 만들고 사용자가 확인·수정 | 라벨 원본, 추출값, 사용자 확인, 직접 입력 경로 |
| 2:30~4:00 | 조건 대조·근거 | 모델·지역·시리얼 등 공지 조건으로 대조하고 공식 다음 행동 제시 | 결과 상태, 미확인 조건, 원문 URL, 자료 시점·관할 |
| 4:00~5:15 | 보관함·후속 조치 | 저장→재검사→변경 안내→사용자 조치 기록 | 사용자별 보관함, 앱 내 알림 동의/해지, 이력 |
| 5:15~6:15 | 정보 부족·장애·긴급 | 검색 실패를 안전으로 바꾸지 않고 긴급 안내를 우선 | 추가 확인 필요, 조회 미완료, 등록 전 긴급 안내 |
| 6:15~7:30 | 구조·개인정보 | OCR과 조건 판정의 역할, 출처 추적, 계정 격리, 내보내기·삭제 | 실제 구조·테스트·데이터 흐름 |
| 7:30~8:45 | 평가·개선 | 자동 테스트, 독립 에이전트 검토, 실제 사용자 평가를 분리 | 실제 건수·분모·실패·수정 내용. 미실시면 미실시 |
| 8:45~10:00 | 운영·확장 | 지원 범위, API·배포 상태, 운영비·담당자, 실증·협력 계획 | 확보한 증거와 미확보 항목을 구분한 준비표 |

## 3. 핵심 설명 예시

### 소개

“배터리체크는 사용자가 가진 보조배터리의 공식 리콜 조건을 확인하고, 필요한 후속 조치와 이후 변경을 관리하는 서비스입니다. 제품 내부 상태나 화재확률을 진단하지 않습니다.”

문제의 발생 빈도·사용자 수·화재 감소율은 검증한 값이 있을 때만 덧붙인다.

### 사진 입력

“사진에서 읽은 값은 후보입니다. 사용자가 라벨과 비교해 수정하고 확인한 뒤 조건 대조에 사용합니다. 사진이 흐리거나 추출 엔진이 없는 환경에서는 직접 입력으로 이어집니다.”

실제 OCR 실패가 생기면 그대로 보여주고 직접 입력한다. 실패 화면을 감춘 채 인식 성공이라고 설명하지 않는다.

### 공식 공지와 조건

“이 결과에는 어떤 공지의 어떤 조건을 비교했는지와 아직 모르는 값이 표시됩니다. 해외 공지라면 해당 국가의 적용 범위를 함께 봅니다. 국내 회수 자격은 제조사 확인이 필요할 수 있습니다.”

“지금 보이는 자료는 `[실제 API 응답 / 공식 웹 검토 저장 자료 / 가상 시험 공지]`이며, 자료 시점은 `[실제 값]`입니다. 지금 대조를 실행한 시각과 자료의 갱신 시각은 별도입니다.”

### 지속 관리

“사용자가 보관함에 저장한 제품을 다시 확인하고, 공지나 결과가 바뀌었을 때 앱 안에서 확인할 수 있도록 구성했습니다. 알림 동의와 해지는 사용자가 제어합니다.”

실제 완성된 동작만 설명한다. 수동 재검사만 검증했다면 “지금은 재검사 시 확인”이라고 말한다. 스케줄러·이메일·문자·푸시를 실행하지 않았다면 상시 자동 감시나 외부 알림을 주장하지 않는다.

“사용자 완료 신고는 사용자가 남긴 기록입니다. 제조사가 회수 완료를 확인한 실적과는 다릅니다.”

### 평가

“소프트웨어 검증은 `[실행한 검사와 실제 결과]`입니다. 별도 에이전트가 `[검토 범위와 발견한 결함]`을 확인했고 `[실제 수정 내역]`을 반영했습니다. 실제 사용자 평가는 `[참여 인원·결과 또는 미실시]`입니다.”

에이전트 평가를 사람이 사용한 결과로 대체하지 않는다. [사용자 검증 절차](USER_VALIDATION.md)의 빈 양식은 준비 자료이며 측정 결과가 아니다.

## 4. 장애 시연과 복구

| 상황 | 시연 행동 | 설명 |
|---|---|---|
| CPSC 503·네트워크 오류 | 조회 미완료와 저장 자료 상태를 확인 | 외부 출처 실패와 제품 안전을 구분 |
| OCR 엔진 없음·추출 실패 | 직접 입력으로 이어감 | 실제 실행 환경의 한계 표시 |
| 필수 조건 미확인 | 제조일·지역·시리얼 질문을 보여줌 | 정보가 부족하면 확정하지 않음 |
| 알림 변화 없음 | 변경 없음·중복 방지 결과 제시 | 알림을 만들기 위해 공식 공지를 변조하지 않음 |
| 통제된 변경 시연 | 가상 시험 공지임을 먼저 표시 | 실제 신규 리콜 발생이나 실시간 감시 실적 아님 |
| 서버·브라우저 장애 | 예비 녹화를 명시하고 확인된 버전 설명 | 실시간 성공으로 표현하지 않음 |

## 5. 예상 질문과 답변 기준

**기존 Safety Korea와 무엇이 다른가?**

사진조회 자체의 새로움을 주장하지 않는다. 개인 제품별 미확인 조건·공지 변경·후속 조치 기록을 연결한 흐름을 설명하고, 직접 검색 대비 사용성 이점은 실제 비교 결과가 있을 때 제시한다.

**왜 AI가 필요한가?**

라벨의 비정형 문자를 읽는 입력 부담을 줄이는 역할을 설명한다. 판정은 공식 조건을 비교하는 규칙으로 수행한다. OCR 실행과 정확도 검증을 구분하며, 생성형 모델/RAG를 실제 사용하지 않았다면 사용했다고 말하지 않는다.

**데이터가 최신인가?**

출처별 마지막 성공·검토 시점, API 실패, 저장 공지 범위를 제시한다. 전체 제품·전체 국가를 실시간 조회한다고 주장하지 않는다.

**제품이 안전하다고 보장하는가?**

확인한 리콜 조건과 사용자 신고 위험징후를 표시하는 서비스다. 검색 결과가 없거나 징후가 보고되지 않은 것은 안전 인증이 아니다.

**개인정보는 어떻게 처리하는가?**

실제 계정·제품·사진 저장 방식을 설명하고, 검증한 사용자 격리·내보내기·삭제 동작을 보여준다. 구현하지 않은 암호화·백업 삭제·법률 검토를 완료했다고 말하지 않는다.

**운영 준비는 끝났는가?**

컨테이너 준비·이미지 빌드·공개 배포·공식 데이터 승인·실제 사용자 실증의 상태를 각각 답한다. [출품 준비표](CONTEST_READINESS.md)의 외부 의존을 공개한다.

**현재 사용자는 몇 명인가?**

팀 내부 테스트, 에이전트 검토, 실제 목표 사용자 수를 분리한다. 실제 사용자 테스트를 하지 않았다면 “아직 미실시이며 준비한 과제로 모집 후 검증할 예정”이라고 답한다.
