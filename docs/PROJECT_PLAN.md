# 배터리체크 프로젝트 기획서

코디세이 AI 네이티브 Final Project용 요약 기획서다. 공모전 제출용으로 쓴 상세 기획(문제 근거, 데이터 확보, 검증 설계)은 저장소 밖의 `배터리체크_개선기획서.md`에 있다. 이 문서의 일정과 역할은 제안이며 팀이 확정해야 한다.

## 1. 문제 정의

보조배터리 리콜 공지는 기관 사이트에 흩어져 있고, 모델명이 같아도 판매지역·일련번호 같은 조건이 붙는다. 소비자는 자기 제품이 해당하는지 확인하기 어렵고, 확인하더라도 이후 조치와 재확인을 잊는다. 한 번 검색하고 끝나는 흐름이 문제다.

배터리체크가 줄이려는 것은 "내 제품에 해당하는 안전 정보를 놓치거나, 확인 후 조치를 미루는 일"이다. 배터리 내부 상태나 화재 확률은 다루지 않는다.

## 2. 타겟 사용자

- 초기: 보조배터리를 쓰는 대학생. 모집과 과제 테스트가 가능한 집단.
- 이후: 일반 소비자, 기숙사·학교 안전 담당자.
- 사용 장면: 리콜 뉴스를 본 직후, 배터리가 뜨겁거나 부풀어 걱정될 때, 예전에 등록한 제품을 다시 확인할 때.

## 3. AI 활용 방식

핵심 기능은 AI 안내 도우미다. 사용자가 "내 배터리 리콜인가요?"처럼 물으면 LLM 에이전트가 필요한 도구를 골라 쓴다.

| 요소 | 쓰임 | 이 방식을 고른 이유 |
|---|---|---|
| AI Agent | 질문에 따라 공식 자료 검색, 내 보관함 조회, 조건 대조 도구를 선택·조합 | 질문 유형이 다양해 고정된 흐름으로는 "내 제품 + 공지 조건 + 다음 행동"을 한 번에 답하기 어렵다 |
| RAG | 저장된 공식 공지와 안전 안내만 근거로 답하고 출처를 표시 | 리콜 조건을 모델의 기억으로 답하면 틀릴 수 있고, 틀린 안내는 안전 문제로 이어진다 |
| Long-term Memory | 계정별 대화와 보관함 기록을 다음 질문에 활용 | 리콜 확인은 한 번에 끝나지 않고 "지난번 그 제품"을 다시 묻는 일이 잦다 |
| 자동화 워크플로우 | 공지 갱신 → 저장 제품 재확인 → 변경 알림 | 사용자가 다시 검색하지 않아도 변경을 알게 한다 |

AI에 맡기지 않는 것: 리콜 후보 판정과 위험징후 안내 문구. 이 둘은 규칙과 검토된 문서로 고정하고, AI는 그 결과를 설명만 한다.

## 4. 기술적 접근

- 프런트엔드 Next.js, 백엔드 FastAPI, 저장소 SQLite, LLM은 OpenAI 호환 API(코디세이 게이트웨이, 도구 사용).
- 사용자가 AI 이용에 동의한 경우에만 질문과 보관함 요약을 외부 API로 보낸다. 사진은 보내지 않는다.
- 검색은 공지 수가 수십 건 규모라 토큰 겹침 기반으로 시작하고, 자료가 늘면 임베딩 검색으로 바꾼다.
- 선정 이유와 구조는 [구현 구조](ARCHITECTURE.md), 요구사항은 [요구사항 정의서](REQUIREMENTS.md)에 있다.
